本报告说明页面切换时内存逐渐增长的原因、已采用的缓解措施，以及后续开发中的预防和回归要求。数字统一使用 MiB，1 MiB = 1,048,576 字节。机器、构建方式、访问的数据和采样时刻会影响内存，不能把不同条件下的单个最低值当成优化结论。此前口述的“约 130 MB”缺少完整操作和采样记录，未作为本次基线。

本轮主要结果：相同七页循环的第 50 轮私有工作集从 319.21 MiB 降至最终方案的 145.35 MiB；预热后的增长量减少约 85.7%。最终方案完成 100 轮后为 157.97 MiB，闲置 120 秒为 157.12 MiB，主页面实例保持 7 个、导航历史保持 0。大幅累积已明显压低，但后半程仍有缓慢漂移，**尚不能证明所有原生内存增长已经消失，也不能保证任意长时间运行绝对不涨**。

## 1. 内存问题与处理目标

| 问题 | 处理 |
| --- | --- |
| 反复切换主页面，内存明显累积 | 清理无用导航历史，为主页面设置有限缓存，并验证缓存页面的进入、离开和数据更新 |
| 后续开发缺少内存回归依据 | 明确资源所有权、离页清理要求和相同负载下的内存回归判断 |

本次采用页面复用来减少重复创建 XAML 视觉树和关联资源的成本，没有在正式程序里加入定时强制 GC、工作集修剪或按任务管理器读数清内存的逻辑。缓存容量限制的是页面数量，不能解释为任意业务负载下的 MiB 硬上限。

### 2.2 指标

| 字段 | 含义与用途 |
| --- | --- |
| `privateWorkingSetMiB` | 当前驻留在物理内存中的进程私有页面；由 `PROCESS_MEMORY_COUNTERS_EX2.PrivateWorkingSetSize` 读取，作为主要观察值 |
| `privateCommitMiB` | 进程私有提交量，由 `Process.PrivateMemorySize64` 读取，辅助判断分配与保留趋势 |
| `workingSetMiB` | 总工作集，包含可共享页面；不能与私有工作集直接混用 |
| `managedMiB` / `managedCommittedMiB` | .NET 托管对象估算量 / GC 提交量；不能代表完整 WinUI 进程 |
| `gc0/1/2` | 各代 GC 次数，区分自然回收与人为干预 |
| `distinctPagesCreated` | 测量期间见过的不同页面实例累计数，**不是当前存活数** |
| `livePages` / `liveNativeRoots` | 弱引用探测的托管页面 / 原生内容根；诊断 GC 后仍存活的缓存页面是预期行为 |
| `backStack/forwardStack` | 导航历史数量，检查无界增长 |
| `handles/threads` | 句柄和线程趋势；短时波动与持续累积应分别处理 |

早期本地探索文件里的 `privateMb` 实际表示私有提交量，`workingSetMb` 表示总工作集；虽然字段含 `Mb`，计算使用的仍是 MiB。它们不能冒充私有工作集。

早期自然 GC 实验仍沿用过 `*-after-gc` 阶段名，是否实际执行人工 GC 以 `collected` 字段为准，不能只看名称。

弱引用探测和日志自身也有少量开销；相同模板的对照承担相同测量开销。

## 3. 相同七页循环的对照

访问顺序：

```text
下载 → 工具 → 设置 → 社区 → 版本库（已安装模式）→ 联机 → 概览
```

每页等待 500 ms，先预热 2 轮，再测量 50 轮，即测量阶段 350 次页面访问；之后闲置 60 秒。测量和闲置阶段均由运行时自然 GC，末尾单独执行诊断 GC。诊断 GC 的结果不计入正常使用成绩。

### 3.3 最终方案的长测与计时器对照

在完整主页面缓存和配套生命周期处理下，计时器复用调整前的一组 100 轮、闲置 120 秒结果如下：

| 阶段 | 私有工作集 | 私有提交 | 托管对象估算 |
| --- | ---: | ---: | ---: |
| 启动 | 84.08 | 118.91 | 6.96 |
| 预热后 | 115.87 | 153.09 | 6.23 |
| 第 50 轮 | 143.81 | 180.40 | 17.26 |
| 第 100 轮 | 160.02 | 195.99 | 15.20 |
| 闲置 120 秒 | 159.29 | 195.64 | 15.61 |
| 末尾诊断 GC | 156.13 | 192.48 | 6.91 |

第 51–100 轮私有工作集范围为 145.32–160.02，斜率约 +0.300 MiB/轮。旧式的大幅增长已明显减小，但仍有缓慢漂移，不应声称“完全不涨”。

窗口字体补刷计时器改为复用一个实例，保留原有 350 ms 补刷，在再次切页时重新计时，关窗停止。最终方案 E 的完整 100 轮、闲置 120 秒结果如下：

| 阶段 | 私有工作集 | 私有提交 | 总工作集 | 托管对象估算 |
| --- | ---: | ---: | ---: | ---: |
| 启动 | 83.88 | 118.98 | 177.30 | 6.92 |
| 预热后 | 117.55 | 154.81 | 223.13 | 6.29 |
| 第 50 轮 | 145.35 | 181.85 | 251.33 | 16.40 |
| 第 100 轮 | 157.97 | 193.79 | 263.13 | 12.46 |
| 闲置 120 秒 | 157.12 | 193.23 | 262.29 | 12.87 |
| 末尾诊断 GC | 148.88 | 185.43 | 254.93 | 6.51 |

E 的第 50 轮较预热增长 27.80 MiB，比 A 的增长量减少约 85.7%，末轮读数减少 173.86 MiB。第 51–100 轮范围为 145.78–159.96，均值 153.60，线性斜率约 +0.263 MiB/轮；第 51–75 轮均值 150.14，第 76–100 轮均值 157.06，相差约 +6.92 MiB。闲置阶段没有继续上升。

这些数值说明页面实例和历史已受控、内存增长明显降低，仍不足以把余下的缓慢增长宣称为完全消除。诊断 GC 的 148.88 MiB 也不能代替正常运行的 157.12 MiB。计时器调整前后的后段均值相近；单次数据不能证明计时器复用单独带来显著降幅，因此保留它的理由是减少资源创建并明确所有权。

计时器复用用于明确窗口资源的数量和所有权。其对内存的单独贡献需要结合重复结果判断，不能把整个页面缓存的降幅归功于这一步。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| C，深色/原标题栏，50 轮，闲置 120 秒 | 159.36 | 203.08 | +43.72 | 199.16 | 190.00 | 15 |
| 完整缓存及配套生命周期处理，浅色/新标题栏，20 轮，闲置 60 秒 | 155.64 | 186.23 | +30.58 | 183.70 | 183.95 | 15 |

## 4. 内存增长原因与证据边界

### 4.1 反复创建页面增加资源分配

缓存前，同一七页负载累计创建 314 个页面实例；完整主页面缓存后为 7 个，且后半程内存增长显著降低。这支持减少页面及其关联资源的重复创建，是本次主要有效的缓解方向。但它不能证明旧页面永久存活，也不能确定所有原生资源的具体保留原因。

### 4.2 导航历史累积有风险，但不是主要增长来源

早期同一 AOT 程序跑 30 轮七页循环，并执行诊断 GC：

| 条件 | 起始私有提交 | 第 30 轮 GC 后 | 差值 |
| --- | ---: | ---: | ---: |
| 原始历史行为 | 121.19 | 260.10 | +138.91 |
| 清理主导航历史 | 119.43 | 252.82 | +133.39 |

历史确有累积风险，主导航没有前进/后退入口，因此保留清理。但是只清历史的内存改善很小，不能把这一步宣称为主要修复。

不要把主 Frame 直接改成 `IsNavigationStackEnabled="False"` 来代替本次处理：现有导航去重依赖 `CurrentSourcePageType`，探索中这种修改导致重复导航和漏掉预期页面访问。该运行不是有效对照。设置页内部 Frame 已禁用历史，并用自己的分类索引去重，条件不同。

### 4.3 页面消失与进程归还内存是不同问题

A 的末尾诊断 GC 能回收旧普通页面及原生内容根，只剩概览和 Required 联机页；私有提交仍为 359.12 MiB。因此，“旧 Page 被全局事件永久引用”不足以解释全部增长。

这支持继续调查 WinUI 原生资源、模板、动画、资源跟踪与分配器的保留行为，但没有完成原生分配调用栈分析，不能据此确认某个 WinUI 类存在泄漏。工作集、私有提交和托管对象数量也不能简单相减，得到所谓“原生泄漏字节数”。

### 4.4 字体、光效及 SDK 尚不能被认定为确定根因

下表均为早期两页循环、20 轮、带诊断 GC 的单次探索，与正式七页自然 GC 场景不同：

| 条件 | 第 20 轮私有提交 | 第 20 轮私有工作集 | 闲置末私有提交 |
| --- | ---: | ---: | ---: |
| 2.5.1 对照 | 207.60 | 167.46 | 206.31 |
| 停止字体遍历 | 193.83 | 152.39 | 193.24 |
| 停止交互光效 | 199.48 | 160.40 | 199.16 |
| 同时停止二者 | 201.34 | 158.36 | 200.93 |
| SDK 2.6.4 stable | 189.02 | 150.67 | 188.60 |
| SDK 2.5.4 experimental | 162.12 | 126.90 | 162.06 |

被跟踪的首轮 642 个控件及旧页面可以消失；停止字体遍历或光效没有消除增长，不能据此认定它们是主要泄漏源。SDK 实验说明框架版本会影响结果，但没有多次重复或完整业务兼容验证，正式项目没有升级 SDK。

之后以方案 E 的缓存和计时器代码、同一冻结模板对 stable 2.6.4 补做 100 轮自然 GC：预热后 116.63 MiB，第 100 轮 166.79 MiB，闲置 60 秒为 164.84 MiB，末尾诊断 GC 为 154.95 MiB。这没有证明升级能改善本项目的正常使用成绩，因此未采用。

另一组旧版两页循环跑到 100 轮，第 30 轮约 180.9 MiB 私有工作集，第 40 轮回落至约 163.3 MiB，第 100 轮约 162.5 MiB，闲置并 GC 后约 161.2 MiB。这组包含人工 GC，只能说明短测持续上涨不等于已经证明“无限增长”，不能代替自然 GC 验收。

在 `Navigated` 后设置页面缓存的尝试没有生效：实例数继续增加，运行被中止。微软要求在页面构造期间启用 Enabled/Required。本次在 Page 根 XAML 中设置，实际实例计数也核实了复用。

## 5. 正式代码的资源所有权

### 5.1 有容量的页面复用

主 Frame `CacheSize=10`。以下十个主页面为 Enabled：概览、版本库、下载、Mod、工具、账户、皮肤、设置、社区、云存档。联机页保留原有 Required 策略以维持会话。

Enabled 可按 Frame 容量淘汰，Required 不受该容量限制。不能把“CacheSize=10”写成“整个应用最多十个页面对象”：联机 Required 页、设置内部四个 Required 分类页以及窗口/对话框另有所有权。

主导航 `Navigated` 清空 BackStack/ForwardStack，保留 `CurrentSourcePageType` 的导航去重。

字体补刷计时器归 MainWindow 所有，窗口内复用一个，导航时重新计时，关窗停止。

### 5.2 页面离开与重入

| 页面 | 重入时 | 离开时或异步回写前 |
| --- | --- | --- |
| 下载 | 重新订阅并刷新后台下载状态 | 解除 ActiveChanged，后台任务由服务继续 |
| 版本库 | 重建所需显示并订阅 InstalledChanged | 解除事件、取消清单/加载器请求、终止子视图过渡 |
| Mod | 更新安装目标并重新搜索 | 取消搜索、移除滚动监听；旧请求不能写回 |
| 账户 | 从账户仓库刷新 | 解除仓库监听、停止卡片动画 |
| 皮肤 | 按导航账户重建选择并刷新预览 | 取消预览、停止帧工作；旧渲染不能写回 |
| 社区 | 新建本轮 token，按登录用户清理私有数据，重新加载；需要时恢复私信轮询 | 停止轮询、取消本轮请求；校验 token、用户和会话后再更新 |
| 云存档 | 清理旧展示并读取当前账号 | 取消列表读取；校验本轮序号、token 和账号，丢弃旧响应 |

社区私信复用一个计时器，防止并发轮询；切换会话后旧响应不能加入新会话。旧请求的 `catch` 和 `finally` 也不能覆盖下一轮的忙碌状态。

云存档上传/下载等已有业务流程没有改成“离开页面即停止传输”；取消的是页面列表读取。真实服务端传输与登录兼容性仍须单独做业务回归。

## 6. 新页面的内存预防规范

### 6.1 缓存与状态

1. 明确页面状态由页面、服务还是窗口持有。需要后台继续的下载/会话交给服务，不能靠泄漏页面维持。
2. 可复用主页面在构造期间或根 Page XAML 设置 Enabled。增加页面时同时评估 Frame 容量；不得为避免淘汰而把所有页面改为 Required。
3. Required 需要具体理由，例如进行中的会话，并记录额外常驻成本。
4. 缓存页的构造函数只执行一次。账号、安装实例、下载状态等必须在重入时刷新。
5. 缓存不会自动清理登录数据。用户变化或退出时，清空私信、草稿、头像、选择和旧用户的私有数据。

### 6.2 事件、异步与渲染

1. 对静态服务、单例、窗口、DispatcherTimer、CompositionTarget 等的监听必须有对称解除；Loaded 多次触发时不能重复订阅。
2. 在 OnNavigatedFrom/Unloaded 停止页面专属计时器、动画、3D 预览和滚动监听，操作应可重复调用；只在实际需要时恢复。
3. 每轮激活使用独立的取消令牌，请求开始时捕获本轮 token/序号/目标 ID。await 后检查它们，再更新 UI。
4. 不要在旧异步流程的后半段读取可变的 `_cts.Token`，那可能已经是下一轮的 token。取消本身也不保证对方不会返回结果。
5. 旧请求的异常处理和 finally 同样需要归属检查，否则可能清掉新请求的 loading 状态。
6. 轮询应避免重叠；切换私信会话、账号或安装目标后，旧结果不能写入新目标。
7. 列表、图片、日志、搜索历史和消息需要明确的数据规模、分页或保留策略。页面数量有限不意味着列表可以无限追加。
8. 不以定时 `GC.Collect`、`EmptyWorkingSet`、`SetProcessWorkingSetSize` 或最小化窗口后的低读数作为修复。人工 GC 仅用于独立的对象存活诊断。

### 6.3 每次改动的测量账目

每个影响页面构造、导航、资源或异步生命周期的改动，至少记录：

- 日期、Git 基点、待提交差异、源码哈希、测量模板哈希、程序哈希、SDK/WinUI 版本。
- Debug 或 Release/AOT，主题、字体、标题栏、窗口状态和测试数据数量。
- 访问顺序、每页等待、预热次数、测量次数、闲置时长；确认实际到达目标页。
- 启动值、预热后值、分轮曲线、末轮增量、后半段均值/范围/斜率、闲置变化。
- 私有工作集和提交量分别报告，附托管堆、GC、页面实例、历史、句柄/线程。
- 正常运行与强制 GC 诊断分列，记录失败和中止原因，不能只保存最好一次。
- 判断是否改善、哪些场景尚未测、下次该复核什么。

一次改动只改变一个因素最易归因；必须同时调整多个因素时，明确记录组合，不能把组合结果归功于其中某一项。不同数据量或不同路由不计算成同一组百分比。

### 6.4 回归判断

新增页面先完整预热，再进行重复的等长测量窗口。检查对象/历史数量是否在预期范围，后半程是否出现有界波动，以及闲置期间是否有意外后台工作。诊断 GC 后的存活页面应能解释其所有权。

本次数据可作为当前环境下的参考基线。后续同场景连续两个后段窗口均值上升超过 `max(10 MiB, 前一窗口均值的 10%)`，或出现超出缓存预算的页面实例、无界历史/句柄增长，应暂停验收并延长测试、定位原因。这个观察线是项目的回归规则，不是微软对内存的保证，也不能证明低于该线的增长永远安全。

发布前至少重复一次关键场景；高波动结果报告多次范围，不能用最低一次替换全部数据。涉及新模型、绑定或序列化时，必须运行发布的 AOT 程序。

## 7. 内存复测流程

复测需要 Windows、.NET 10 SDK；Native AOT 还需要 Visual Studio C++ 构建工具。以下步骤沿用已有测量口径；仅重新构建或手工查看任务管理器，不能代替完整复测。

1. 在隔离源码副本和独立数据目录中构建待比较版本，不复制真实 LocalSecrets、账号令牌或私人数据。记录第 6.3 节要求的版本、环境和哈希；对照版本使用相同的采样实现。
2. 按第 3 节顺序访问七个主页面，每页等待 500 ms，预热 2 轮，再执行 50 轮并闲置 60 秒。长测延长至 100 轮、闲置 120 秒。采样必须确认实际到达目标页，不能只计算点击次数。
3. 按第 2.2 节分别记录私有工作集、私有提交量、托管堆、GC 次数、页面实例、导航历史、句柄和线程。保存启动、预热后、每轮及闲置样本，计算增量与后半程范围、均值、斜率。
4. 正常测量依靠自然 GC；需要检查对象存活时，在全部正常采样结束后单独执行诊断 GC。不得将诊断 GC 后的最低读数作为正常运行成绩。
5. 扩展场景按第 3.4 节的页面、数据量和等待时间执行。主题、字体、标题栏、SDK 或测试数据变化时单独分组，不与原场景混算改善比例。
6. 涉及社区或云存档生命周期时，在隔离副本中用合成只读响应验证离页取消、重入刷新和旧响应丢弃，尤其要让旧响应在取消后返回。真实登录、消息收发和云端传输仍须另做集成验证。
7. 按第 6.4 节判断回归。保留每次成功、失败和中止的本地记录；发布前至少重复一次关键场景，并将实际条件、结果和未覆盖项写入报告。

## 8. 尚未解决的内存增长与适用边界

最终方案完成 100 轮切页后私有工作集为 157.97 MiB，闲置 120 秒后为 157.12 MiB。页面实例和导航历史数量已受控，后半程仍有约 +0.263 MiB/轮的缓慢增长，尚未完全定位和消除。不能据此宣称任意长时间运行都不会继续增长。

社区和云存档的生命周期检查覆盖了实例复用、离页停止轮询、重入刷新、退出账号后清理数据及丢弃旧响应。这些检查支持资源归属与取消机制的正确性，但不能代替长期内存压力测试。

部分补充实验在同一台机器上并行执行，窗口焦点及系统后台负载没有完全固定；最终计时器补跑单独执行。当前数据用于工程回归和定位，不是多机器统计性能结论。

真实社区服务器、真实账号私信、云端上传/下载/同步、持续下载或游戏运行、大量自定义皮肤与长列表没有全部纳入内存压力场景。合成数据检查只证明对应客户端生命周期分支，不能推断服务端协议、权限和网络失败的全部行为。

未取得需要管理员权限的 WPR 原生分配跟踪，因此没有给出原生分配栈或声称已经确认框架内部具体泄漏点。若后续在相同场景仍持续增长，应保存程序版本与曲线，再按微软的方法采集 VirtualAllocation/堆分配，比较增长区间的保留分配和调用栈。
